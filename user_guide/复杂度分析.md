# 37 项宽表 SQL 探针算法复杂度分析

> 基于 `results-sqlrun-compare-2g/summary.md`（MySQL vs cjserver）和内核代码实现（`src/` 各模块），
> 逐项分析当前实现、未完成优化、以及优化后的渐进复杂度。

## 符号约定

| 符号 | 含义 | 典型值（110 万行场景） |
|---|---|---|
| N | 表总行数 | 1,098,342 |
| M | LSM 层的 SST 数量（L0+L1+L2） | 10-30 |
| R | 查询返回/影响行数 | 1-50（点查）或 68-100（范围） |
| K | LIMIT 值 | 5-100（个别探针 1000） |
| C | 每行 JSON 列数 | 25 |
| G | GROUP BY 分组数 | 3-40 |
| H | 跳表高度 | log₂(N) ≈ 20 |
| Z | 全表扫描需访问的块数 | N / 块大小 |
| B | BlockCache 命中额外开销 | 常数 |
| D | 位图/倒排命中 doc 数 | 因条件而异 |
| S | 倒排段数 | 10-20 |
| T | 倒排 FST 词典大小 | 字段字典项数 |
| F | fsync 开销 | ~0.1ms（组提交共享）或 ~0.3ms（逐次） |

## 一、点查（#1-#4）

### #1 pk_point_star（`SELECT * FROM t WHERE id=?`）

| 项 | 值 |
|---|---|
| **当前实现** | LSM 点查：布隆过滤 → 逐层 SST 定位 → HotCache 命中直接返回 / BlockCache 块读 → 整行 JSON 反序列化 |
| **当前复杂度** | O(log M) + O(C) JSON 解码 |
| **未完成优化** | 无（P2-D `batch_get` + 两级缓存已完备） |
| **优化后复杂度** | 同左，常数级优化空间有限 |
| **实测** | 0.27ms vs MySQL 0.21ms = 1.3×（同档） |

### #2 pk_point_proj10（`SELECT 10 列 FROM t WHERE id=?`）

| 项 | 值 |
|---|---|
| **当前实现** | 同 #1，整行 JSON 解码后再投影 10 列 |
| **当前复杂度** | O(log M) + O(C) 解码 25 列 → 投影 10 列 |
| **未完成优化** | P3-B PAX 列存：仅解码目标列，跳过其余 15 列的反序列化 |
| **优化后复杂度** | O(log M) + O(10) 而非 O(25) |
| **实测** | 0.49ms vs MySQL 0.16ms = 3.1×（行存每列都解码导致 3× 差） |

### #3 pk_in_5（`SELECT * FROM t WHERE id IN (5点)`）

| 项 | 值 |
|---|---|
| **当前实现** | P2-D `batch_get()`：批量回表，LSM 有序性 + BlockCache 局部性 |
| **当前复杂度** | O(5 log M) + `batch_get` 批量常数优化 |
| **未完成优化** | 无 |
| **优化后复杂度** | 同左 |
| **实测** | 0.46ms vs MySQL 0.19ms = 2.4×（同档） |

### #4 pk_in_50（`SELECT * FROM t WHERE id IN (50点)`）

| 项 | 值 |
|---|---|
| **当前实现** | P2-D `batch_get()` 50 个 docid 批量获取 |
| **当前复杂度** | O(50 log M) + `batch_get` 批量 |
| **未完成优化** | 无 |
| **优化后复杂度** | 同左 |
| **实测** | 1.92ms vs MySQL 0.38ms = 5.1×（50 个点查累计，LSM 层数多时偏慢） |

## 二、范围查询（#5）

### #5 pk_between_100（`SELECT * FROM t WHERE id BETWEEN a AND b`）

| 项 | 值 |
|---|---|
| **当前实现** | docid 窗口流扫描：`scan_stream(start, end)` → 每行 JSON 解码 |
| **当前复杂度** | O(R) + O(R × C) 解码 100 行 × 25 列 |
| **未完成优化** | 行存解码 25 列是主要开销（MySQL 紧凑行存 1KB 加载，无需 JSON 解析） |
| **优化后复杂度** | O(R) + O(R × 1) 列存解码 |
| **实测** | 4.05ms vs MySQL 0.29ms = 14×（JSON 解码开销大） |

## 三、倒排/枚举（#6-#9）

### #6 enum_sel_limit100（`SELECT * FROM t WHERE status='active' LIMIT 100`）

| 项 | 值 |
|---|---|
| **当前实现** | 倒排 FST 查找 term → RoaringBitmap 候选 → `batch_get()` 批量回表 → LIMIT 100 |
| **当前复杂度** | O(log T) + O(K) 位图遍历 + O(100) 回表 + O(100 × C) 解码 |
| **未完成优化** | 无 |
| **优化后复杂度** | 同左 |
| **实测** | 4.20ms vs MySQL 0.52ms = 8.1×（回表 100 行 × 25 列 JSON 解码是主因） |

### #7 enum_count（`SELECT COUNT(*) FROM t WHERE status='active'`）

| 项 | 值 |
|---|---|
| **当前实现** | Ex-9.3 倒排统计载荷：term `status=active` 预存储 `doc_count`，直接返回 O(1) |
| **当前复杂度** | O(1) — 倒排 FST 索引查找 + 读取已存储的 doc_count |
| **未完成优化** | 无 |
| **优化后复杂度** | 同左 |
| **实测** | 0.66ms vs MySQL 64.39ms = **0.01×（快 98×）**— 倒排载荷方案显著优于 MySQL 二级索引扫描 |

### #8 combo_and（`SELECT * FROM t WHERE status='active' AND region='east' LIMIT 100`）

| 项 | 值 |
|---|---|
| **当前实现** | 两个倒排 term 各自 RoaringBitmap → 位运算 AND 交集 → `batch_get()` 批量回表 |
| **当前复杂度** | O(log T₁) + O(log T₂) + O(min(|R₁|,|R₂|)) 位图 AND + O(100) 回表 |
| **未完成优化** | 无 |
| **优化后复杂度** | 同左 |
| **实测** | 3.49ms vs MySQL 0.61ms = 5.7×（回表 100 行 JSON 解码是主开销） |

### #9 field_in（`SELECT * FROM t WHERE status IN ('a','b','c')`）

| 项 | 值 |
|---|---|
| **当前实现** | 每个 IN 值独立倒排查找 → bitmap 并集 → `batch_get()` 批量回表 |

## 四、扫描（#10-#11）

### #10 cmp_gt_limit50（`SELECT * FROM t WHERE amount > 500000 LIMIT 50`）

| 项 | 值 |
|---|---|
| **当前实现** | P1-E Zone Map 块级剪枝：SST 每块存储 amount 列 min/max；块不相交则跳过；命中则 JSON 解码若干行，早停在 LIMIT=50 |
| **当前复杂度** | O(Z<sub>after</sub> × B) — Z<sub>after</sub> = 块级剪枝后剩余块数（远小于全表 Z） |
| **未完成优化** | 无 |
| **优化后复杂度** | 同左（Zone Map 已接线） |
| **实测** | 2.47ms vs MySQL 2.04ms = 1.2×（同档） |

### #11 cmp_between（`SELECT * FROM t WHERE amount BETWEEN 730000 AND 740000`）

| 项 | 值 |
|---|---|
| **当前实现** | P1-E Zone Map 剪枝 + 行扫描解码。无 amount 列索引，仍需扫描大量块 |
| **当前复杂度** | O(Z<sub>after</sub> × B) — 剪枝后仍 ~30% 块需扫描，每行 JSON 解码 25 列 |
| **未完成优化** | P3-B PAX 列存：仅解码 amount 列，跳过其余 24 列反序列化 |
| **优化后复杂度** | O(Z<sub>after</sub> × B) 但每行解码从 O(25) → O(1) |
| **实测** | 6686ms vs MySQL 505ms = 13.3×（JSON 解码 25 列是主瓶颈） |

## 五、聚合（#12-#15）

### #12 count_all（`SELECT COUNT(*) FROM t`）

| 项 | 值 |
|---|---|
| **当前实现** | P1-C keys-only 扫描：`count_all_docs()` 调用 `scan_stream_ids` → 遍历所有 key（不解文档值） |
| **当前复杂度** | O(R<sub>blocks</sub>) — 仍需扫描所有 SST 块的 key<br>遍历 110 万 key |
| **未完成优化** | O(1) 增量记账：engine 在 put/delete/flush 时增量维护 doc count，持久化到 manifest；启动时一次性恢复基线 |
| **优化后复杂度** | **O(1)** — 直接返回计数器值 |
| **实测** | 5868ms vs MySQL 186ms = 31.6×（当前最慢探针之一）<br>**优化后预期：** <1ms |

### #13 sum_where_enum（`SELECT SUM(amount) FROM t WHERE status='active'`）

| 项 | 值 |
|---|---|
| **当前实现** | 倒排等值 → bitmap 候选 → 批量回表 34 万行 → 解码 amount 累加 |
| **当前复杂度** | O(D) — D≈34 万行回表 + 每行 JSON 解码 |
| **未完成优化** | P1-D 倒排统计载荷：term 预存储 SUM/AVG/MIN/MAX 统计 → 段级累加 |
| **优化后复杂度** | O(S) — S=10-20 段，每段读取预聚合的 sum 值 → 直接返回 |
| **实测** | 6524ms vs MySQL 399ms = 16.4×<br>**优化后预期：** ~500ms（统计载荷 + Zone Map 进一步剪枝） |

### #14 group_by_status（`SELECT status, COUNT(*) FROM t GROUP BY status`）

| 项 | 值 |
|---|---|
| **当前实现** | 全表扫描 + HashMap 分组累积。当无 WHERE 且单字段时，走 Ex-9.3 倒排词典枚举快路径 → 每个 term 读取 doc_count |
| **当前复杂度** | 快路径：O(M) M=3 个不同 status 值<br>回退全扫：O(N) + O(G log G) |
| **未完成优化** | 无（快路径已存在） |
| **优化后复杂度** | 同左 |
| **实测** | 6435ms vs MySQL 338ms = 19×（快路径应在 110 万行也命中，但实测仍是全扫，需检查接线） |

### #15 group_by_sum_having（`SELECT status, SUM(amount), COUNT(*) GROUP BY status HAVING COUNT(*) > 0`）

| 项 | 值 |
|---|---|
| **当前实现** | 全表扫描 + HashMap 分组累积 + HAVING 过滤 |
| **当前复杂度** | O(N) + O(G log G) + O(G) HAVING 过滤 |
| **未完成优化** | 无本质优化空间（HAVING 依赖分组后过滤） |
| **优化后复杂度** | 同左 |
| **实测** | 6507ms vs MySQL 2094ms = 3.1×（MySQL 二级索引覆盖扫描，cjserver 全表扫） |

## 九、新增 11 项探针（#27-#37）

### #27 group_by_multi（`SELECT status, region, COUNT(*) FROM t GROUP BY status, region`）

| 项 | 值 |
|---|---|
| **当前实现** | 全表扫描 + HashMap 双字段分组。因两字段分组，不发倒排词典枚举快路径 |
| **当前复杂度** | O(N) + O(G log G) G=分组数（status×region ≈ 3×6=18） |
| **未完成优化** | **倒排多字段枚举组合**：分别枚举 status 和 region 的 term → 笛卡尔积累积。分组基数小时，从 O(N) 降为 O(M₁×M₂) |
| **优化后复杂度** | 快路径：O(M₁ × M₂) M₁=3, M₂=6 → 18 次 term 查询<br>全扫回退：O(N) 同左 |
| **实测** | 6894ms vs MySQL 513ms = 13.4×（全表扫是主因） |

### #28 having_avg_gt（`SELECT status, AVG(amount) ... GROUP BY status HAVING AVG(amount) > 500000`）

### #29 orderby_multi（`SELECT * FROM t ORDER BY k, amount LIMIT 100`）

| 项 | 值 |
|---|---|
| **当前实现** | 全表扫 → 候选集 > 200,000（SORT_MAX_ROWS）→ 安全阀 1064 拒绝<br>（P0-B Top-K 堆已实现，但 110 万行全表扫 + 批量回表 + 堆排序仍约 19s） |
| **当前复杂度** | 无 LIMIT：O(N) 全扫 + O(N log N) 全排序 → 拒绝（1064）<br>有 LIMIT：O(N) 全扫 + O(N log K) 堆排序（K=100） |
| **未完成优化** | ① P0-B Top-K 堆已实现，但 110 万行全扫 + 堆排序本身仍慢<br>② 可优化：SST 层预排序，多路归并时利用段内有序性提前终止<br>③ 可优化：增加 Zone Map 下推到 ORDER BY 列，减少扫描量 |
| **优化后复杂度** | 当前已完成 P0-B：O(N) + O(N log K)<br>**远期优化：** 减少 N（Zone Map 下推）或 N 不降但常数更优 |
| **实测** | 10 万行：19s（MySQL 649ms）<br>110 万行：拒绝（1064）<br>**优化后预期：** 110 万行 ~1-2s |

### #30 composite_idx_point（`WHERE status='active' AND ts=?`）

| 项 | 值 |
|---|---|
| **当前实现** | status 倒排 bitmap → 22 万行候选 → 批量回表 → 逐个过滤 ts 等值 |
| **当前复杂度** | **O(K)** — K ≈ 22 万行，全部回表 + JSON 解码 |
| **未完成优化** | **P0-A 组合索引**：引擎 `query_by_composite_prefix()` 已实现，SQL 层未接线。<br>组合索引 (status, ts) 直接前缀扫描，无需回表过滤 |
| **优化后复杂度** | **O(log N + R)** — R=1 行（等值命中），前缀扫描直达目标行 |
| **实测** | 921ms vs MySQL 411ms = 2.2×（MySQL 无组合索引时也慢）<br>**MySQL 加组合索引后：0.30ms**<br>**优化后预期：** <10ms（千倍级收益） |

### #31 composite_idx_range（`WHERE ts BETWEEN ? AND ?`）

| 项 | 值 |
|---|---|
