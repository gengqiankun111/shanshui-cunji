## 四、已知差异项与后续优化方向（不阻塞收口）

1. **#6/8/9 枚举等值 SELECT（含 LIMIT 100）慢**：等值倒排命中 ~22 万 posting（active 组），
   eval 返回全位图后 execute 对全量 posting batch_get 回表再切片——LIMIT 未下推到回表前。
   MySQL 走 idx_status LIMIT 100 只取 100 行。**修复方向**：倒排位图消费端对 LIMIT 早停
   （位图迭代取前 k 个 docid 再 batch_get，对应 optimizer_proces 阶段 7 LIMIT 下推——Top-K 位图
   迭代取 k 先行）。10 万轮 2 万 posting 17ms、110 万轮 22 万 posting 729ms，与 posting 数线性
   一致，证实为全量回表所致。**注**：#7 enum_count 走倒排载荷（doc_count）已 0.29ms，证明
   位图索引本身正常，纯消费端缺 LIMIT 下推。
2. **#29 orderby_multi（ORDER BY k,amount LIMIT 100）慢**：k 无索引，110 万全扫物化候选 +
   全排序 17.9s；MySQL filesort 576ms。**修复方向**：Top-K 堆在扫描中流式维护（P0-B 已实现
   Top-K 但需确保走 topk_sort 而非全量收集排序路径——本探针候选集 110 万 > SORT_MAX_ROWS
   触发全排序守卫？实际 rows=100 输出说明走了 topk；耗时 17.9s 疑为 batch_get 全量候选回表 +
   排序键提取，同 #6 的 LIMIT 未下推问题同源）。
3. **#25/35/36 事务（RR/SERIALIZABLE）3× 慢**：cjserver 默认 flush_log_at_trx_commit=1
   （逐 COMMIT fsync 强安全）；MySQL 该实例 innodb_flush_log_at_trx_commit=2。P2-A 已提供
   档位 2（组提交窗口），对比公平性可后续用 `--flush_log_at_trx_commit 2` 复测。
4. **#5 主键范围 pk_between_100 2-4ms**：docid 窗口扫描含 memtable/SST 归并，MySQL 主键
   B+Tree 页读更快。后续可评估 keys 区间扫描优化。

### 5.2 判定：①（LIMIT/回表未下推同源问题）是否已消除

- **①-a：#6/8/9 枚举等值 SELECT 的 LIMIT 未下推回表 —— ✅ 已消除**。
  110 万轮 729/97/1207ms → 3.50/3.52/3.62ms（-99.5% ~ -99.7%，208×/28×/333×），
  10 万轮同步收敛至 ~3ms；对 MySQL 比值从 820×/143×/1749× 落至 3.8–5.7×
  （剩余差为 LSM 回表点查 vs MySQL 覆盖索引 LIMIT 的结构差，非全量物化）。
  P85 `collect_limited_rows`（512/块早停 + 墓碑不占位）达验收线并超额。
- **①-b：#29 ORDER BY 全量候选回表 —— ⚠️ 未消除（部分改善，收口移 P91）**。
  110 万轮 17.9s → 13.1s（-27%），仍 25.3× MySQL；未达 P87 ≤1.5s 验收线。
  根因：1.1M 候选仍逐 docid 投影点查回表（`batch_get_fields` 每 docid 独立定位，
  ~11µs/docid）——P87 流式化消除了全量物化峰值内存，但**点查型取数**取代了
  全量 batch_get 物化，耗时未见量级下降；P86②/P87② 的按需解码只省了解码列数，
  未省点查定位开销。
  另：PAX（`storage.hot_fields=["k","amount"]`）实验轮中 #29 实测 18.9s（不降反升），
  且该布局下**通用全扫/聚合路径整体回归 5–8s**（PAX 块行式解码路径未优化）——PAX 化
  #29 路径亦未达线。→ **残余瓶颈（点查定位 → 扫描流式取数 + 通用 scan 投影列）收口
  入 P91（见 development_remain）**；届时 #29 候选走 docid 窗口块流式扫描解码排序键，
  目标 ≤1.5s。
- **结论：①（同源"消费端全量物化/回表后再切片"）中 LIMIT 侧（#6/8/9）已消除；
  ORDER BY 侧（#29）仅消除内存物化峰值（O(N) 峰值 → O(K+chunk)），时延收口待 P91。**

### 5.4 本轮顺带验证（不阻塞）

- P90 PAX 块级 SUM/COUNT 下推：因本轮行式布局（无 hot_fields）块级路径不触发（eligible
  要求全 PAX 块）→ SUM/COUNT(f) 走行级精确路径，语义正确（无回退误报）；PAX 布局下聚合
  回归属"PAX 通用扫描路径未接线"（P91 收口），非 P90 块级下推本身问题。

  窗口"执行 → 默认表 [0,2^48) 窗口仍走 keys-only 全扫（407ms）——O(1) 需窗口全包时直通
  count_all_docs（可优化项，随 P91/后续）。
