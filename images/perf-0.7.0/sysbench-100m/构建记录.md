## P0 优化复测（M 项范围扫描一次化 + N 项 batch_get，commit d044b4c）
2026-08-31 新 binary 重启 3308 后重测事务类（8 线程 20s）：

| 测试项（rand） | 旧 binary TPS / mean | 新 binary TPS / mean | 提升 |
|---|---|---|---|
| oltp_read_only (special) | 42.2 / 189.3ms | **70.9 / 112.7ms** | **+68%** |
| oltp_read_write (special) | 29.5 / 269.9ms | **53.0 / 150.7ms** | **+80%** |
| oltp_read_only (uniform) | - | 68.0 / 117.5ms | |
| oltp_read_write (uniform) | - | 58.0 / 137.6ms | |

**结论与瓶颈诊断**：
- M 项（BETWEEN/SUM 从逐 id 展开改为 `scan_range_txn` 一次快照扫描）生效：事务类 +68%~80%，读延迟 -40%。
- **未达预估 ~50×**。单连接计时实测（3308，10 条语句/连接）：点查与 100 行范围 SUM 均亚毫秒级（范围 0.2ms/条）——**scan_range_txn 本身不慢**。
- 真实瓶颈 = **引擎全局单 Mutex 每语句串行**（mysql.rs `Arc<Mutex<Engine>>`，每条 COM_QUERY 持锁执行 ~1ms）。8 线程 × 14 语句/事务排队 → 服务器吞吐天花板 ≈ 1000 stmt/s（70 TPS × 14 语句 = 980 stmt/s，与点查 5k TPS = 0.2ms/语句的串行上限吻合）。
- **后续 P1 方向**：① 读路径 `RwLock` 化（RR 快照读只读，读读并行，需读 API 化 &self）；② MySQL 层事务内语句批处理（BEGIN..COMMIT 合并 dispatch，省 13 次锁往返）；③ 快照读走 HotCache（get_at 可加 per-txn 小缓存，不污染全局热缓存）。

## P 项事件驱动自动 Compaction 上线验证（2026-08-31，commit 24861c6）
- **背景**：1 亿库构建期无自动合并，78 个 L0 段全部留在读路径（点查逐段布隆+索引定位）。
- **验证**：新 binary 重启后，单条 INSERT 触发写路径 `auto_compact` —— 78 个 L0 段**同步合并收敛为 1 个 L1 段**（~10.8GB，合并耗时约 5-6 分钟，期间写入阻塞 = 背压语义）；INSERT 完成后数据完整可读（id=100000001 回查命中）。
- **效果**：oltp_read_only（special，8 线程 20s）：
  | 阶段 | TPS / mean | 对比基线 |
  |---|---|---|
  | 基线（旧代码，78 L0） | 42.2 / 189ms | - |
  | M 项后（78 L0） | 70.9 / 113ms | +68% |
  | **P 项合并后（1 L1 段）** | **75.8 / 105ms** | **+80%** |
- **结论**：点查从 78 段遍历降到 1 段仅 +7%——印证事务类瓶颈是**引擎全局 Mutex 串行**（O 项，~1000 stmt/s 天花板）而非 SST 遍历；SST 收敛的主要价值是文件数/读放大可控（防 78 段无限堆积）。

## O 项第②步 RwLock 读读并行上线验证（2026-08-31，commit 4585bb9）
- **背景**：引擎读方法 `&self` 化（HotCache/txn_locks/pending_inverted/SstReader.full_index 内部 Mutex）+ mysql.rs `Arc<Mutex<Engine>>` → `Arc<RwLock<Engine>>`，读语句（SELECT/SHOW/SET）读锁并行、写语句写锁互斥。
- **效果**（8 线程 20s，special）：
  | 测试项 | P 项后（Mutex，1 SST） | **O 项第②步（RwLock）** | 提升 |
  |---|---|---|---|
  | oltp_read_only (special) | 75.8 TPS / 113ms | **560.9 TPS / 14.3ms** | **+640%** |
  | oltp_read_write (special) | 53.0 TPS / 151ms | **230.3 TPS / 34.7ms** | **+334%** |
  | oltp_read_only (uniform) | 68.0 / 117.5ms | 335.9 / 23.8ms | +394% |
  | oltp_read_write (uniform) | 58.0 / 137.6ms | 209.4 / 38.2ms | +261% |
- **结论**：突破 ~1000 stmt/s 串行天花板——read_only 42→561 TPS（**13.3× 基线**）、read_write 29.5→230 TPS（**7.8× 基线**），事务平均延迟 -87%；剩余写侧串行（txn_commit 写锁）+ max 尾延迟（flush/compaction 停顿）留 O 项第③步（ssts ArcSwap 后台合并）与写路径并行。

## O 项第③步 ssts ArcSwap 原子发布 + 后台合并上线验证（2026-08-31，commit e9f7d39）
- **背景**：O 项第②步（RwLock 读读并行）已突破读串行天花板，但合并仍由写路径同步执行（持写锁，读被阻塞）；第③步将 ssts 改为 `ArcSwap<SstSnapshot>` 原子发布，合并移入后台 worker（读锁下执行）。
- **改动**：`ssts → ArcSwap<SstSnapshot>`（读 load 无锁快照 / 写 store 原子切换）+ CF/Engine compact 全链 `&self` + 写路径 `auto_compact` 双分支（挂载 worker 只置 `compact_pending` 信号；无 worker 保持同步背压）+ mysql `spawn_compaction_worker`（100ms 信号轮询 + 10 分钟兜底，`try_read` 读锁合并）。
- **效果**（8 线程 20s，`--db-ps-mode=disable`，与 O② 基线同参数）：
  | 测试项（rand） | O 项第②步 TPS / mean | **O 项第③步** | 对比 |
  |---|---|---|---|
  | oltp_read_only (special) | 560.9 / 14.3ms | 519~550 / 14.5-15.4ms | 持平（±噪声） |
  | oltp_read_write (special) | 230.3 / 34.7ms | 245.7 / 32.5ms | +6.7% |
  | oltp_read_only (uniform) | 335.9 / 23.8ms | 550.6 / 14.5ms | +64%（状态差异+噪声） |
  | oltp_read_write (uniform) | 209.4 / 38.2ms | 236.8 / 33.8ms | +13% |
- **后台合并端到端验证**（小库 3309：l0_stall_threshold=2 / l0_max_size_mb=1 / memtable 8MB）：写路径 flush → 置 `compact_pending` → worker 100ms 内 `try_read` 读锁合并——日志连续出现 "刷盘完成 → Compaction 完成: →L1/L2 合并 2 段 → 1"；合并后数据完整可读（点查 8.1k TPS）；多轮合并收敛到 2 个 SST。
- **写路径行为澄清（非 O③ 回归）**：oltp_insert 8 线程在本库污染后（WAL 回放 110 万条 + 3 SST）由 24k/s 降至 ~4k/s——A/B 验证（stash O③ 改动重建 O② 版本同测 4.2k/s）确认 **O② 版本同样掉速**，属既有写路径（delta.delete_prefix/组提交窗口）在脏状态下的表现，与 O③ 无关。
- **结论**：O 项三部曲完结——读路径无锁化（&self → RwLock → ArcSwap 后台合并），合并不再阻塞读；事务类 TPS 无回归、写侧略升；430 测试全绿。

## 架构评审六项落地（R/T/V/W/X/U，2026-08-31，388a916/0eca7a5/f09e9fb/0257835/85b9a62）
- **R 项**（388a916）：层布隆 OR 合并数学不可行（P62）→ 层/段两级 Zone Map 范围粗筛（点查层遍历整层跳过 + 段级越界跳过，零假阴性零格式变更）；demo 16 段点查 ≈ 单段（0.95×）。
- **T 项**（0eca7a5）：事务 256 项快照缓存（RR 同 key 二次读直达，提交/回滚即弃）。
- **V 项**（f09e9fb）：crates/io-uring-file（Linux 门控独立 crate，io-uring 0.7 同步提交-等待 + SQPOLL/绑核，交叉 check 通过）+ 主库 IoUringPool + SQPOLL 核预留（热路径接入留 Linux 部署验证）。
- **W 项**（f09e9fb）：跨列族紧迫度调度（compaction_urgency：L0×10+大小超限+8），每轮压最高紧迫度档，worker 多轮收敛。
- **X 项**（0257835）：Prometheus 风格 /metrics（计数器 + 延迟对数直方图，引擎/列族/网络分层埋点）。
- **U 项**（85b9a62）：SstRangeIter 组读预读（4×4KB → 1×16KB，布局校验失败回退逐块）。
- 测试 430→437 全绿。

| 配置 | oltp_insert TPS | bulk_insert TPS |

- **写路径瓶颈定位与修复（2026-09-01，后续 A/B 深挖）**：初始归因"auto_compact 写后合并背压"，A/B 隔离
  排除合并——实为 **`needs_compact` 大小条件每次 put 调 `l0_bytes()`（fs::metadata × L0 段数）的 syscall
  风暴**：`l0_max_size_mb>0` 且 L0≥2 时每次写入 3 次文件 stat → 写吞吐崩塌。
  | 配置 | oltp_insert TPS | 说明 |
  |---|---|---|
  | 原（l0_max_size_mb=1024） | 2,676 | 每 put 3×stat |
  | B（auto_compact 关） | 18,404 | 跳过检查 |
  | C（l0_max_size_mb=0） | 25,103 | 短路大小条件 |

  （open/flush/compact 构建快照时填）→ `l0_bytes()`/`sst_bytes()` 读缓存求和，写路径 needs_compact 零 syscall。
- **修复后全量写/读**（原配置，8 线程 15s）：oltp_insert 23,964 / bulk_insert 210,895（+45×）/

## 六项后 1 亿库复测结论（无回归确认，2026-08-31）
- read_only（8 线程 20s special）复测 57 TPS（O③ 回滚对照 69 TPS）——**同量级，非本批六项回归**。
- **根因**（P67 记录）：此前 O③ 519 TPS 时 memtable（WAL 回放 473MB）覆盖 sysbench 查询热点（5000 万附近）→ 事务范围查询内存命中；当前 memtable（110 万 insert 数据）热点落 SST 冷区 → 事务范围查询冷块读 7-8ms → 事务类 TPS 降至 ~60。单语句诊断：点查 0.4-1.5ms 正常、非事务范围 1.4ms 正常、事务范围 7-8ms（冷块读）。
- **结论**：R/T/V/W/X/U 六项无读路径回归；事务范围冷块读延迟为 M 项后既有行为，U 项预读已覆盖一部分，剩余可后续优化（如事务范围块级缓存）。
