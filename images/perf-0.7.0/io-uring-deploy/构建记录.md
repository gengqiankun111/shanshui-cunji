# io_uring Linux 部署实测构建记录（V 项收尾，7.71）

2026-09-01 在阿里云 Debian 12 完成 io_uring 部署实测（development.md 7.71）。

## 环境
- 服务器：阿里云 Debian 12 (bookworm)，内核 **6.1.0-52-amd64**（io_uring 符号 342，完整支持）
- 硬件：2 核 / 1.6GB 内存 / 40GB 盘（1.6GB 编译大依赖需 `CARGO_BUILD_JOBS=1` 防 OOM）
- 工具链：Rust 1.96.0（rustup 默认 static glibc）+ gcc（zstd-sys）
- 客户端：pymysql 2.2.8（服务器本地回环 127.0.0.1:3307，无 RTT）
- 配置：组提交 2ms / WAL append / memtable 8MB（强制 flush 使读走 SSTable）/
  `[runtime] io_uring_enabled=true|false` A/B 切换 / affinity 关闭

## 热路径接入（补 7.63 缺口，本会话代码变更）
7.63 时代 `iou` 池仅初始化、未接入读写热路径（A/B 无差异）。本次接入：
- `SstReader` + `open_with_io_uring`：块读（read_block/read_block_group/block_raw）经
  `read_at_io` 转发 → SQPOLL（IoClass::Sst 队列）或同步 read_at
- `WalWriter`/`RingWal` + `set_io_uring`：fsync 经 `fsync_file` 转发（IoClass::Wal 队列）
- `ColumnFamily::open_with_io_uring`：加载的 SST 与 WAL 注入池；engine 池创建提前传入三 CF
- io-uring-file crate 补 `unsafe impl Send`（Arc 跨线程派发，白名单论证）

## 启动验证
- io_uring ON 日志：`io_uring 后端池初始化成功（SQPOLL 三队列，预留核=Some(0)）`
- OFF 日志：`io_uring 未启用（runtime.io_uring_enabled=false），走同步 IO`

## A/B 实测（30 万行，memtable 8MB 已落 1 个 SST，读走 SSTable 块读）
| 指标 | io_uring ON | 同步 OFF | 结论 |
|---|---|---|---|
| 写吞吐 rows/s | 17,174 | 19,695 | -13%（SQPOLL 占核） |
| 写 P50/P95 ms | 55.1 / 59.1 | 47.6 / 55.4 | ON 略慢 |
| 点查 5k qps | 23 | 23 | 持平（块缓存主导） |
| 点查 P50/P95 ms | 44.0 / 47.9 | 44.0 / 44.6 | 持平 |
| 扫描 30×100k /s | 1.3 | 1.3 | 持平 |
| 扫描 P50/P95 ms | 747 / 766 | 751 / 761 | 持平 |

**结论**：io_uring 池/热路径正确生效（SST 块读 + WAL fsync 走 SQPOLL），但 2 核小机器
SQPOLL 内核轮询线程占用 1/2 核资源，写路径反降 13%；点查/扫描由块缓存主导、IO 非瓶颈故
持平。符合 7.63 指引预期——收益在核多/高 IOPS 场景显著。

## 核隔离验证
`reserve_sqpoll_core` 生效：3 个 `iou-sqp-53282` 内核线程（WAL/SST/倒排三队列）
全部绑定**核 0**，业务主线程在**核 1**（2 核机器 SQPOLL 独占 1 核）。

## 决策
- io_uring 保持**默认关**（`io_uring_enabled=false`）——小机器负收益
- 多核 NVMe 生产环境按 7.63 指引开启 + affinity 预留 SQPOLL 核
