一、TinyLFU 核心原理
TinyLFU 的本质是 Count-Min Sketch（频率草图）+ 定期衰减 + Doorkeeper 过滤器，用固定内存近似统计海量 Key 的访问频率。

为什么内存不到 1MB？

text
传统 HashMap（100万 Key）：100万 × (Key 8B + Value 1B + 指针 8B + 开销) ≈ 20-30MB
TinyLFU：固定数组 512 × 512 = 262144 个 4-bit 计数器 = 1MB
组件	原理	内存
Count-Min Sketch	4 个哈希函数映射到 512×512 二维数组，每个计数器 4-bit（0-15）	1MB
Doorkeeper	Bloom Filter 过滤低频项，防止 sketch 被长尾污染 	可忽略
Reset 机制	每 100 万次访问，所有计数器右移一位（÷2），保持统计新鲜度 	0 额外内存
查询频率时：取 4 个哈希位置的最小值（最小值最接近真实，因冲突只会上报偏高不会偏低）。

核心结论：TinyLFU 用计数精度换空间（4-bit 只能计到 15），配合定期衰减，使得高频 Key 能持续被识别，低频 Key 不会长期霸占统计空间。

1. 你的理解完美拆解
“4个哈希函数，每个映射到512x512数组”

✅ 完全正确。这 512x512 的二维数组，就是一个紧凑的频率表。每个格子是一个 4-bit 的计数器（只能数 0 到 15）。4 个哈希函数，意味着每个 Key 会在数组中命中 4 个不同的格子。

“统计的可能是其他数据，hash值一样也加进来了统计”

✅ 完全正确。这就是哈希冲突。
Count-Min Sketch 不存储 Key 本身，只存储哈希后的位置。假设 Key1 和 Key2 在第一个哈希函数上落到了同一个格子，那么它们俩的访问计数会累加到一起。

“所以是用了这4个哈希函数的访问频数统计的最低值”

✅ 完全正确。这就是 Count-Min Sketch 保证精度的核心算法。
因为同一个 Key 的计数被分散到了 4 个独立的格子里。冲突（其他数据）只会让计数偏高，永远不会让它偏低。
因此，当我们查询 Key1 的频率时，取这 4 个格子里的最小值，这个值就是最接近真实频率的值，完美排除了哈希冲突带来的噪音！

2. 为什么这套机制能保证高精度？
原理：Count-Min Sketch 的核心是“最小估计”。

场景：假设 Key_A 真实访问 100 次，Key_B 和它冲突，Key_B 访问了 50 次。

4 个格子中，只要有 1 个格子没有 Key_B 的干扰，那么那个格子的值就是 100，其他带干扰的格子是 150。

取最小值（100），我们得到了精确值！

数学保证：只要哈希函数足够随机，4 个格子同时被严重污染的概率极低。即使有轻微污染，取最小值也能将误差控制在极小的范围内。

3. 拓展：TinyLFU 的“与时俱进”机制
你理解了核心原理后，我再补上 TinyLFU 最后一块拼图，让它变成一个工业级可用的组件：

问题：4-bit 最大值是 15，如果某个 Key 被访问了 1000 次怎么办？
方案：它不是永远计数的，而是每隔一段时间（比如每 10 万次查询），把数组里所有的计数器除以 2。

效果：访问 1000 次的热点 Key（1000 → 500 → 250...），永远保持在较高水平。

冷数据回收：访问 5 次的冷数据（5 → 2 → 1...），很快就归零，从草图里被遗忘了。

这就是为什么 TinyLFU 只需要 1MB 内存：它不记录"总共访问多少次"，只记录 "最近一段时间内访问了多少次"，过期数据自动蒸发。

二、落地规划（2026-09-05，Task-027 优先开发；对齐现有 src/hotcache 结构）
定位：HotCache **读回填准入端**缺失——目前 put/invalidate 只走写路径（write.rs），读命中 LSM 后不
回填（防扫描型污染也牺牲了纯读负载预热）。TinyLFU 作为**准入过滤器**：读 miss 时 Record(docid)，
Estimate ≥ 门槛（默认 3）才 put/promote；与淘汰端现有 LFU 采样近似互补（准入过滤 + 淘汰分级）。

组件落地（src/hotcache/）：
1. tinylfu.rs：Count-Min Sketch（4 哈希 × 512 列 × 4-bit 饱和 0-15，内存 ~0.5-1MB 可配）+ Record/
   Estimate(min of 4)/reset(全量 >>1)。
2. doorkeeper：Bloom 过滤首访——首见 key 先进门卫（低成本放行第一二次），防 sketch 被长尾首访污染；
   准入判定 = doorkeeper 命中 || Estimate ≥ 门槛。
3. 衰减 reset：累计 **Record 样本数 ≥ N** 触发全量 >>1（见 §三 问答）。
4. 接线：engine 读回填点（LSM 命中后）走准入；写 put 保持直写不回绝（新写入即时可读性优先）；
   invalidate 不清 sketch 单 key（CMS 无法精确删）→ 清 doorkeeper 位 + 靠衰减自然淡出。
5. 单测/验收：见 development_remain Task-027。

三、衰减设计问答（用户 2026-09-05）
Q1 是否要“自己配”？——不建议用户配“多少次查询”。查询/命中率/QPS 是负载属性，配查询数会让窗口随
负载漂移。**参数化“采样计数阈值 N”**（可配、有默认）即可，用户免配即用。
Q2 动态计算还是固定？——采用**固定采样计数触发（简） + 参数可调（灵）**：每次 Record 令样本 n+=1，
当 n ≥ N 全量 >>1。N 默认动态推导 = 4×width（512×512=262144 → **N=1_048_576 ≈ 104 万**，与 doc 头
“每 100 万次访问”一致）；配置 `reset_samples=0` 即用默认（免配），>0 覆盖。
Q3 到底多少次查询衰减一次？——衰减周期不是“查询次数”，而是**按 Record 事件数**：每累计约 104 万次
Record 全量减半一次。换算直观口径：若每次读命中 LSM 都 Record（纯读负载），则平均每 **N / 读QPS**
秒衰减一次（如读 10 万 QPS → 约每 10.5s 一次；100 万 QPS → 约 1s 一次）——高 QPS 衰减更勤，
“最近热度窗口”时长随之收窄，语义正确且无需人工调。
Q4 4-bit 饱和上限？热点反复访问计数封顶 15，靠衰减 ÷2 持续保持高位（15→7→15），冷数据（3→1→0）
自然蒸发，不需用户干预。
